# Risk Register — Zeker

**Created:** 2026-09-01, from the first weekly review and the first MBR.
**Shape:** `mantis/meetings.md` §6. Each role owns its own entries; **nobody owns the
file as a whole.**

A **risk** has not happened, could, and would cost something if it did. That is
different from a **finding** (already true) and a **blocker** (already stopping
work). An **accepted** risk stays here with its acceptance recorded — accepting a
risk is a decision (the Founder's authority), not a deletion.

This register closes a gap the Founder-Facing Audit Duty already assumed existed:
several roles are obliged to raise *"what exposure is accumulating that no one has
decided to accept"*, and until today there was no register for that answer to
accumulate in. Everything below had been raised in prose somewhere and had nowhere
durable to land.

**Status key:** 🔴 open, unmitigated · 🟡 open, partly mitigated · 🟢 mitigated ·
⚪ accepted, recorded

## Security & privacy

| # | Risk | Impact | Owner | Mitigation / status |
|---|---|---|---|---|
| R-01 | **Nobody checks that whoever registers a building actually runs it.** Held together, our records say where a named individual lives. If the creator is not the administration, the whole legal justification for storing "apartment 302 = María García" is gone | Company-ending if discovered by a journalist rather than by us | Security Engineer / Founder | 🟡 **D-006 answered 2026-09-04, after being open since 2026-08-27: a person approves each building** (Decision 018). A new organization cannot add anybody or issue a permit until approved — the boundary is not "can the product be used" but "can data about somebody other than the account holder enter it". Approval is an operator script (`npm run aprobar`), never a route, so no privileged role exists inside the product to be stolen. Seven tests. **Absent means approved**, so nothing that existed before today is affected. 🟡 **Open until it is proven in a browser**, and with one named gap: an unapproved administrator **has no way to reach us** — Zeker sends no email and has no contact address (D-008). That is the interface audit's "no next action" failure, on purpose and written down rather than discovered later |
| R-02 | **Any organization admin can create Firebase accounts for arbitrary email addresses, unmetered**, each triggering a Google-sent email naming the recipient. Chained with one throwaway signup, this is a spam/phishing relay wearing our identity | Discovery by Google's abuse desk rather than by us | Security Engineer | 🟢 **Capped 2026-09-04**, and with two limits rather than one because one is not enough. `max_members` (25) is the plan limit and goes down when somebody is removed. **`max_invites_per_day` (15) is the control that actually bounds this**, and it is never given back on removal — a cap that only counts current members is defeated by adding twenty people and removing them, and those twenty emails have already left. Both are checked **before** the Firebase account is created, so a refusal leaves no orphan account and sends nothing. Changing an existing member's role consumes neither, or the cap would trap the administrator instead of the abuser — **which is a real bug the tests caught before it shipped**. Nine tests. 🟡 **Still unproven in a browser**, and the numbers are a judgement, not a measurement: nobody has watched a real building set itself up |
| R-03 | **Our own action-handler page can become an account-enumeration surface** if it renders the address `verifyPasswordResetCode` returns — the obvious, friendly thing to do | Undoes protection the recovery screen went out of its way to build | Software Architect | 🟡 Known before the code exists. Security Engineer signs off before merge |
| R-04 | **Isolation between organizations depends entirely on backend code** and has **never been proven live** against two real organizations on the deployed system | One customer sees another's residents | Security Engineer | 🟡 16 tests. | R-05 | **Privacy policy and terms do not exist.** Ley 1581/2016 requires the privacy policy before the first real customer | Legally cannot launch | Regulatory & Data Privacy Counsel — **not active, flagged since 2026-08-26** | 🔴 Carried across three sessions |

## Added 2026-09-03, after a routine publish took the product down

| # | Risk | Impact | Owner | Mitigation / status |
|---|---|---|---|---|
| R-28 | **A publish erases every API setting that is not written in the deploy script.** `scripts/desplegar.sh` uses `gcloud run deploy --set-env-vars`, which replaces the service's whole environment rather than adding to it. On 2026-09-03 the API's `CORS_ORIGINS` had been set by hand in the console and existed nowhere in the repository, so a normal publish wiped it. `LOG_LEVEL` went with it | **The entire product went down for several minutes**, and the message it showed was *"revise su conexión a internet"* — which sends a person to look for the fault in their own network. A customer seeing this would conclude the product is broken and be unable to say why | DevOps Engineer / Software Architect | 🟡 **Mitigated for the known case, open in general.** `CORS_ORIGINS` is now declared in the script with a comment saying what it broke. **Nothing checks that the script's list is complete** — the next setting somebody types into a console will disappear at the next publish, silently. **This is the fourth instance in three days of the same shape** (R-25, R-26, R-16): a value that lives in exactly one place no process respects. The durable fix is that the deploy script is the only place any of it is set, and that is a convention, not a mechanism. 🟢 **The fix held its first real test**: the 2026-09-03 deploy of Decision 015 carried `CORS_ORIGINS` through, checked on the live revision afterwards. Proved by a real deploy, not reasoned about |

## Added 2026-09-02, after auditing what this development machine actually holds

| # | Risk | Impact | Owner | Mitigation / status |

| R-23 | **The whole company's infrastructure is reachable from one unlocked laptop.** `~/AppData/Roaming/gcloud/application_default_credentials.json` holds an `authorized_user` **refresh token for the Founder's own Google account** — not a service-account key, a standing grant that renews itself. `~/.config/configstore/firebase-tools.json` holds a second one for the Firebase CLI. Anyone who opens a session on this machine acts as the Founder in `zeker-505918`: read and write Firestore, redeploy or delete Cloud Run, rewrite the security rules, change the API key, delete the project. **Verified today, not assumed:** production configuration was read and modified from this machine with no re-authentication.
